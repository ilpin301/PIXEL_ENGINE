# Prompt: Design and Develop a Cross-Platform Pixel Game Engine for Microcontrollers

## 1. Role and Expertise

Act as a senior embedded systems engineer, game engine architect, graphics programmer, and low-level C/C++ developer specializing in resource-constrained hardware.

You have deep practical experience with:
- Embedded systems and microcontroller architectures.
- STM32, ESP32, RP2040, and similar microcontrollers.
- 2D graphics engines and pixel-art rendering.
- Game development frameworks and engines.
- Bare-metal programming, HAL, FreeRTOS, and hardware abstraction.
- DMA, SPI, I2C, parallel display interfaces, and memory optimization.
- Tile-based worlds, procedural generation, collision detection, and game physics.
- Performance optimization for systems with limited RAM, flash, CPU performance, and bandwidth.

Your task is to design and help implement a reusable **Pixel Game Engine (PGE)** that allows developers to create 2D pixel-art games inspired by games such as Terraria, Starbound, and classic 16-bit platformers, but specifically optimized for microcontrollers.

The engine should be practical enough to run on real embedded hardware, not just exist as a theoretical architecture.

## 3. Main Objective

Design a modular, portable, lightweight 2D Pixel Game Engine capable of supporting games with Terraria-like mechanics.

The engine should provide a foundation for creating games featuring:
- Pixel-art graphics.
- Tile-based maps and environments.
- Large scrolling worlds.
- Procedurally generated terrain.
- Multiple layers of tiles.
- Character movement and animation.
- Collision detection.
- Physics and gravity.
- Inventory systems.
- Items and crafting.
- Interactive objects.
- Enemies and basic AI.
- Health and damage systems.
- Particle effects.
- Lighting and environmental effects, where hardware permits.
- Sound effects and music, where hardware permits.
- Menus, HUDs, and UI elements.
- Save/load functionality.

The architecture must be scalable: a small platformer should work on a low-end microcontroller, while more ambitious games should take advantage of more powerful hardware.

Do not assume that every microcontroller can run every feature. Design a capability-based system that enables or disables expensive features depending on available resources.

## 4. Hardware Targets

Design the engine with hardware abstraction and portability as core principles.

Initially target the following platforms:

| Platform | Purpose |
|---|---|
| ESP32 | General-purpose embedded gaming |
| ESP32-S3 | More demanding graphics and processing |
| STM32F429I-DISCO | Reference STM32 graphics platform |
| STM32F4 series | General STM32 compatibility |
| STM32H7 series | Higher-performance embedded gaming |
| RP2040 / RP2350 | Additional portable target |

Do not limit the architecture to these platforms. It should be possible to add new microcontrollers without rewriting the engine.

For every supported platform, consider:
- CPU performance.
- Available SRAM and external RAM.
- Flash capacity.
- Display resolution.
- Display color depth.
- Display controller and interface.
- Available DMA controllers.
- Hardware timers.
- Input peripherals.
- Audio output capabilities.
- Available storage (SD card, external flash, etc.).

Create a hardware capability profile that the engine can use to determine which features are available.

## 5. Graphics and Rendering Architecture

This is one of the most important parts of the project.

Design an efficient rendering pipeline suitable for microcontrollers.

Investigate and compare:
- Framebuffer rendering.
- Partial framebuffer rendering.
- Scanline rendering.
- Tile-based rendering.
- Dirty rectangle rendering.
- Sprite batching.
- Hardware-assisted rendering using DMA.
- Direct-to-display rendering.

The architecture should support:

### Graphics primitives
- Individual pixels.
- Lines.
- Rectangles.
- Filled rectangles.
- Circles.
- Sprites.
- Transparent sprites.
- Sprite sheets.
- Animated sprites.
- Tilemaps.
- Text rendering.

### Rendering features
- Multiple rendering layers.
- Camera movement.
- Camera scaling, if feasible.
- Parallax scrolling.
- Sprite transparency.
- Palette-based rendering.
- Clipping.
- Sprite flipping and rotation where practical.
- Basic particle effects.

### Color formats
Evaluate RGB565, RGB888, indexed 8-bit color, and other appropriate formats.

Prioritize memory-efficient rendering and allow different rendering backends depending on the hardware.

For example, a device with insufficient RAM for a full framebuffer should still be capable of rendering a game using smaller buffers or scanline-based techniques.

Provide realistic memory calculations for different display resolutions and color depths.

## 6. World and Game Systems

Design a lightweight game-world architecture inspired by Terraria's tile-based approach.

The engine should support:

- Chunk-based world storage.
- Tile-based terrain.
- Multiple tile layers.
- Tile properties and metadata.
- Chunk loading and unloading.
- Procedural world generation.
- Collision maps.
- Interactive tiles.
- World boundaries.
- Camera-based rendering.
- Entity management.
- Object pooling.

Consider how to represent large worlds when the microcontroller has only tens or hundreds of kilobytes of RAM.

Investigate:
- Chunk dimensions.
- Compressed world storage.
- Procedural reconstruction.
- External storage.
- Lazy loading.
- Cache management.

Separate game-specific systems from engine-level functionality.

## 8. Software Architecture

Design the engine as a collection of independent modules.

Propose a clean architecture with components such as:

1. Core — engine lifecycle and initialization.
2. HAL — hardware abstraction layer.
3. Platform — MCU-specific implementations.
4. Graphics — rendering API.
5. Renderer — platform-specific rendering backends.
6. Display — display drivers.
7. Sprite — sprite and animation management.
8. Tilemap — tile-based world rendering.
9. Camera — camera and scrolling.
10. Input — unified input management.
11. Audio — sound and music.
12. Physics — movement, gravity, and collisions.
13. Entity — entity and object management.
14. World — chunk-based world management.
15. Resource Manager — asset loading and caching.
16. Storage — save/load functionality.
17. UI — menus and HUD.
18. Debug — performance statistics and diagnostics.

Define clear interfaces between these modules.

The engine should be written primarily in **C++17 or later**, with C-compatible interfaces where useful.

Avoid unnecessary dynamic memory allocation, excessive inheritance, heavyweight STL usage, and expensive abstractions.

Prefer:
- Static allocation where practical.
- Memory pools.
- Fixed-size containers.
- Compile-time configuration.
- Data-oriented design.
- Predictable execution times.
- Optional feature modules.

Explain every major architectural decision and its trade-offs.

## 9. Developer API and Game Creation Experience

The engine must be pleasant to use.

Design a simple API that allows developers to create games without needing to understand the underlying hardware.

For example, the API could look conceptually like this:

```cpp
#include <PixelEngine.h>

class MyGame : public Game {
public:
    void onCreate() override {
        loadSpriteSheet("player", "player.bmp");
        setWorldSize(128, 128);
    }

    void onUpdate(float deltaTime) override {
        if (Input::pressed(Button::LEFT)) {
            player.move(-1, 0);
        }

        if (Input::pressed(Button::RIGHT)) {
            player.move(1, 0);
        }
    }

    void onRender(Renderer& renderer) override {
        renderer.clear(Color::Black);

        renderer.drawTilemap(world);
        renderer.drawSprite(player);
    }
};

int main() {
    PixelEngine engine;
    engine.start<MyGame>();
}
